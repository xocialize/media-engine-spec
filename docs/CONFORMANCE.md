# MES conformance catalogue (suite 0.1)

The tests the conformance suite runs (Base §16; Image profile §5). Each one checks a requirement the spec states.

**Engine tests** run only when they apply: for the features the engine claims, the mode it runs in, and the
operations it offers. A test that doesn't apply is skipped with its reason, and doesn't count against conformance.

```bash
swift run mes-conformance engine http://127.0.0.1:17600/mes/v0
```

```bash
swift run mes-conformance engine https://192.168.1.20:17600/mes/v0 --pair
```

- **Paired engines:** `--pair` pairs as part of the run, which also tests pairing (BASE-090); the engine's operator
  approves. `--paired-state <dir>` reuses a `mes pair`, and `--token` with `--pin` passes credentials directly.
- **Retention:** checked by observation. Output expiry (BASE-071) is observed when `outputs_ttl_s` is at most
  `--max-ttl-wait` (30 s by default).
- **Grants on a LAN engine:** `--grant-host` gives this machine's address as the engine sees it.
- **Reports:** `report.json` and `report.md` are written to `-o <dir>`. The command exits 0 when the engine
  conforms.

**Client tests** run the client against a scenario-mode mock engine that records every request and plays a
situation: busy, no capacity, a failed or cancelled job, an unknown error code, or outputs gone. For each scenario the
client does one task, generating an image from a prompt and saving it. The suite then judges it from the engine's
side: what it sent and when, what it left holding, and how it exited. The default client is `mes`. Any command-line
client can be tested with a shell template:

```bash
swift run mes-conformance client
```

```bash
swift run mes-conformance client --command 'my-client --engine {url} --prompt {prompt} --out {out}'
```

The tables below are generated by `swift run mes-conformance list`.

## Client tests

Each runs against a scenario-mode mock engine; the scenario is what the engine does to the client.

| Test | Checks | Spec | Scenario |
|---|---|---|---|
| CLIENT-001 | Every request names the Base version (MES-Version: 0.1) | §2 rule 3 | `normal` |
| CLIENT-002 | Job requests use only described inputs and parameters, valid against the descriptor | §7.1, §16 | `normal` |
| CLIENT-003 | One submission per task, and following the job doesn't busy-poll | §7.3, §11 | `normal` |
| CLIENT-004 | What the client collects, it confirms or releases: no job is left holding | §7.3, §13, §16 | `normal` |
| CLIENT-005 | The task completes: the job's output is fetched and the client exits 0 | §7 | `normal` |
| CLIENT-010 | 429 busy: waits for Retry-After, then retries and completes | §7.1, §12, §16 | `busy` |
| CLIENT-011 | 503 no_capacity: waits for Retry-After, then retries and completes | §12, §16 | `no-capacity` |
| CLIENT-020 | A failed job is reported as a failure; no outputs are fetched and nothing is resubmitted | §7.2, §16 | `failed` |
| CLIENT-021 | A job cancelled on the engine is reported, and no outputs are fetched | §7.2, §16 | `cancelled` |
| CLIENT-022 | An unknown error code is handled by its HTTP class: reported, and a 4xx isn't retried | §12 | `unknown-error` |
| CLIENT-023 | Outputs that are gone (410) are reported, not retried in a loop | §7.3, §13 | `gone` |
